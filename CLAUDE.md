# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Hector, a small hexapod: 6 legs, 2 DOF each, 12 Waveshare SC09 bus servos. `hector.c` is a single-file C REPL that started as a copy of `../servo/servo.c` (the generic SC09 tester, https://github.com/op12no2/servo) and keeps all its commands; the hexapod commands (`stand`, `sit`, `front`, `legtest`, `ident`, `offset`, `calibrate`, `walk`, `set`, `loads`, `imu`, `selftest`) are in the `/* ---- hexapod ---- */` section. The same file builds for the ATOM S3R: `atom/` is an ESP-IDF project whose only source is `../hector.c`, and the I/O section near the top (`/* ---- I/O ---- */`) has an `ESP_PLATFORM` half and a POSIX half; nothing else differs, so keep it that way. Fixes to the servo layer (protocol, `move`, the line editor) likely belong in `../servo` too. Its `CLAUDE.md` has the details of the SC09 and the adapter: register behaviour, move overshoot, the unreliable moving flag, the dead zone and so on. There are no tests and no dependencies beyond libm.

## Hardware

- **Host:** either the Raspberry Pi 5 (where Claude Code runs) via the Waveshare Bus Servo Adapter (A) over USB (stable path `/dev/serial/by-id/usb-1a86_USB_Single_Serial_*`), jumper in B, or the ATOM S3R (the on-board controller) via the adapter's UART header, jumper in A; 1 Mbps either way. The ATOM's USB is its console and flashing port, `/dev/serial/by-id/usb-Espressif_USB_JTAG_serial_debug_unit_*`. Both enumerate as `/dev/ttyACMn`, so use the by-id paths (`./hector`'s default `/dev/ttyACM0` may be the ATOM). The gait code has no I/O of its own besides `send_pose()` and `send_leg()`.
- **ATOM wiring** (`wiring.md`, `wiring.svg`; built 2026-10-02 with patch leads; D1 fitted by 2026-10-05, so the ATOM can run from the battery through the buck, with USB plugged in or not; until then the buck's 5V lead was unplugged and the ATOM ran from USB): ATOM G38 (TX) / G39 (RX) / GND to the adapter's 3-pin UART header H2 (GND, RXD, TXD, named for the host: RXD to RX, TXD to TX), jumper in A (B = the adapter's USB, for the Pi); `BUS_TX`/`BUS_RX` in `hector.c`. The adapter's UART side is 3.3 V (LVC buffers), so no level shifting. Power: battery through the MPM3610 5 V buck and a Schottky into the ATOM's 5V pin, which is the same net as its USB VBUS (so the diode stops the buck and a USB port back-feeding each other). The adapter's own 5 V/3.3 V aren't brought out. G39, G38, 5V, GND are the ATOM's right-hand header in that order; Port A (G2 SDA, G1 SCL) is kept for the sensor.
- **Servos:** SC09, 300° over 0..1023 (0.293°/step), 2.3 kg·cm. Supply is a 2S LiPo straight to the servos (rated 4.8–8.4 V).
- **Geometry:** `cad/README.md` has the parts, how they fit together, the foot position and body height against `height`, and clearances measured in CAD. Since 2026-09-26 the body is a 220 mm disc with a central wiring cage, the hips are 90 mm from the centre, and the legs reach 91.5 mm from the lift axis. The parts share one coordinate frame; `05_one_hip_assembly.step` has the body, lid and one leg's parts as named components, which is the easiest to measure. To measure the STEP files, `pip install cadquery-ocp` (Open CASCADE; aarch64 wheels exist) into a venv. Its OCP 8 API needs `Bnd_Box.CornerMin/CornerMax`, not `Get()`, `TopoDS.Face`/`Vertex`/`Edge`, not `Face_s` etc., and `OCP.OCP.collections.Sequence_TDF_Label` for a `TDF_LabelSequence` (read the assembly with `STEPCAFControl_Reader` and `XCAFDoc_DocumentTool.ShapeTool_s`). All-up weight was about 500 g with the old 164 mm body; the new body and lid are about 50 cm³ more plastic, not yet weighed.
- **Legs:** hip (yaw) servos are ids 1–6, lift servos 7–12; leg n = hip n + lift n+6. Nominal (stand) position is 511 for all, plus `offset[]` (below). Lifts can go up to the servo limit but only about 50 steps below 511 before the leg hits the chassis (the user judges 50 itself OK); `DOWN_MAX` (50) clamps that in `send_pose()`. That was on the old body; in CAD the new one has the same margin as the old (the leg meets the plate's outer ring), so 50 should still hold, but it hasn't been checked on the robot. `height` runs from -`SPLAY_MAX` (-150: stance legs 150 above centre, body lower, legs splayed) to `DOWN_MAX`. Hips can easily do 300 either way; `HIP_MAX` (150) clamps them, as neighbouring legs can meet. In CAD, though, turning a hip towards the side its leg plate is on (the same rotation for every hip, as all six legs are fitted the same way round: forward on one side, back on the other) brings the leg's lower half against the plate's outer ring, sooner the lower the foot: about 123 steps at `height` 0, 61 at +50, 177 at −60. A walk's hip swing is up to stride + turn, plus the swing curve's overshoot (≈9% in tripod).
- **Overload protection** (Waveshare's SCS memory table, https://files.waveshare.com/upload/5/5c/SCS_Series_Memory_Table_Analysis.xls; the SC09s here hold its defaults): if a servo's load (0x3C, the drive duty cycle in 0.1%) stays over the overload torque (0x27, 80%) for the protection time (0x26, 100 × 40 ms = 4 s), its output drops to the protection torque (0x25, 20%) and its status reports overload (bit 5). Unloading conditions (0x13) = 0x20, i.e. only overload protection enabled. A lift servo is loaded all the time its foot is down, so standing still and slow gaits (a wave stance at an 800 ms step is 4.0 s) are the risk, more than fast ones.
- **Gains:** every servo came with P 15, D 15, I 0 (0x15–0x17, EPROM). On 2026-10-05 the six lifts were set to **I 1** (`lock 7-12 0; wb 7-12 0x17 1; lock 7-12 1`): with I 0 a lift only drives in proportion to its error, so it holds the body 1–4 steps off its goal, friction leaves it wherever it lands, and its load reads only 0 (dead zone), 6, 7.5, 9%; with I 1 it pushes its foot onto its goal (error 0–2) and its load is the force on that foot, in finer steps. Standing loads then came out within 1.0–1.4% of each other on every stand (four sit/stand cycles, nearly identical), and `calibrate` balanced in one round with no offset change. The hips are still I 0. The self test checks the gains (`P_GAIN`, `D_GAIN`, `I_HIP`, `I_LIFT`), so a replaced servo with factory settings gets flagged with the commands to fix it. Walking compared on 2026-10-05 (default wave, `walk 2` forward and `walk 2 -50` back, each with I 1 and then I 0): the peak loads were the same within run-to-run noise, all under 26%; lifts 8 and 12 (legs 2 and 6) peaked at 22–26% in every run against 9–17% for the rest, either setting. The user couldn't see any difference either, so the lifts stay at I 1. A side effect: a lift with no weight on it (after `sit`, or a leg lifted) twitches a few times as the I term overshoots by a step and corrects, then settles; the user likes it ("very organic"). A lift that kept twitching would be working all the time (battery, heat). To go back: `lock 7-12 0; wb 7-12 0x17 0; lock 7-12 1`.
- **Servo 9** (the lift of leg 3, LR) was replaced on 2026-10-01 (the old one went into overload protection and sagged). The new one replies as id 9 and holds the default overload settings.
- **Offsets:** `offset[]` (per id) is added to every goal position sent, by `move` and by `leg_goals()`, so with `[7] = 20`, `move 7 511` sends 531. At 511, the RF and RR feet (lifts 10 and 12) were off the ground; the user set them to -20, then `calibrate` (2026-10-01, height 0, battery lead centred) gave 7:+4 8:-8 9:+3 10:-21 11:+3 12:-24; rerun on 2026-10-05 (on the ATOM, height 0) from those, it balanced in 3 rounds (spread 7% → 1%, mean 8%) at 7:+4 8:-7 9:+3 10:-23 11:+5 12:-25, and again the same day after the electronics cage went on top (battery freshly charged, 8.1–8.6 V) in 4 rounds (0–16.5% → 9–10.5%) at 7:+4 8:-7 9:+2 10:-26 11:+9 12:-25. A foot that is high needs a negative lift offset. As `DOWN_MAX` applies before the offset, lifts 10 and 12 can go about 20 steps further down than the others; fine if the offset makes up for a horn set off true (the chassis contact moves with it), not checked. Reads (`pos`, `stat`, `verify_move()`) are raw servo positions; `ww` to 0x2A doesn't add it.
- **Layout and directions:** `legs[]` (layout, `hip_dir`, `lift_dir`) as first written walked the robot correctly without changes, so the guesses were right; the layout was redone on 2026-10-05 for the current numbering (see Leg numbering). If a leg is rebuilt, check its directions before walking: a wrong `lift_dir` would drive the swing legs down into the chassis. `legtest` lifts to 700 (189 above centre), well past the 50-step chassis margin if `lift_dir` is wrong, so on a rebuilt leg check the lift direction with a small `move` first.

## Build / run

```
make                               # cc -O2 -Wall -Wextra -o hector hector.c -lm
./hector [/dev/ttyACM0] [baud]     # defaults: /dev/ttyACM0, 1000000
echo "walk 2" | ./hector           # non-tty stdin works for scripted commands

cd atom && source ~/esp/esp-idf/export.sh   # the ATOM build (ESP-IDF v6.x at ~/esp/esp-idf)
idf.py build && idf.py -p /dev/serial/by-id/usb-Espressif_* flash
```

To script the ATOM's REPL (it has no non-tty mode: it always line-edits and echoes), open its port with DTR and RTS both false before opening (pyserial: set `s.dtr = s.rts = False`, then `s.open()`), or the chip resets, and end lines with `\r\n` or `\r`. The IDF venv (`~/.espressif/python_env/*/bin/python`) has pyserial.

Keep the build warning-free under `-Wall -Wextra`. Walking can only really be verified on the robot; if you can't test on it, say so. Never make it move unless the user is there: it can walk off the desk.

## Architecture (hexapod section)

- **I/O (`/* ---- I/O ---- */`):** the bus (`open_port`, `bus_flush`, `bus_write`, `read_bytes`), the console (`con_init`, `con_tty`, `con_raw(block)`, `con_restore`, `con_getc`, `con_drop`), ctrl-c (`sigint_catch`/`sigint_restore`, `halted`), `msleep` and walk's fixed-rate ticks (`tick_start`, `tick_wait`). On the ATOM the bus is UART1 (TX G38, RX G39, a pull-up on RX) and the console the USB-Serial/JTAG driver: no termios and no SIGINT, so `con_tty()` is always 1 and ctrl-c arrives as byte 3, which `walk` checks for (`idf.py monitor` passes it through). There is no TX echo over H2, unlike the Waveshare USB adapter: `BUS_ECHO` (0 in the ESP half, 1 in the POSIX half) tells `txrx` whether to read back and drop the echo. Don't set it where there's none: that read asks for as many bytes as were sent, so a reply shorter than the packet (every write's is 6 bytes) made it wait the whole 50 ms timeout, which cost `stand` 0.6 s on the ATOM until 2026-10-05 (`stand` measured 1.85–2.0 s, 1.25–1.4 after). The line editor reads the bytes after an escape with a 50 ms timeout, so a lone escape key doesn't stall the idle loop. `sdkconfig.defaults` sets 1 ms FreeRTOS ticks (bus timeouts are a few ms) and a 16 KB main task stack (`move`/`verify_move` keep several `int[254]` on the stack). With no USB host, console output is dropped rather than blocking. The line editor treats CR LF as one enter, as `idf.py monitor` sends both.
- **`legs[]`:** per leg, side (0 left, 1 right) and row (0 front, 1 middle, 2 rear), hip and lift ids, `hip_dir` (+1 if a higher position swings the foot forward), `lift_dir` (+1 if a higher position raises the foot), and the current state `x` (hip, + forward) and `z` (lift, + up from the stance pose), in servo steps.
- **`send_pose(tm)`:** turns every leg's x/z into 12 goal positions (applying dir, `height`, the clamps and `offset[]`) and sends them as one `SYNC_WRITE` (`sync_move()`, which takes a position per id) with goal time tm. It and `send_leg()` (one leg's two servos, for `legtest`, which leaves the other legs where they are) are the only things that command the legs; both go through `leg_goals()`.
- **`gaits[]`:** a gait is the fraction of the cycle each leg is in the air (`swing`) and each leg's offset in the cycle, indexed by [side][row]: wave (one leg at a time, back to front, right side then left), ripple (two), tripod (three).
- **`walk()`:** streams a pose every `TICK_MS` (20 ms, goal time 20). Global phase advances by dt/period (period = `step` / `swing`). On the ground a leg's hip sweeps back at 2·amp per stance time. That rate is the same for every foot on the ground, so no foot slips. In its swing window a leg lifts (z = lift·sin πw) and its hip follows a cubic (Hermite) from its lift-off x to `amp`, starting and ending at the ground rate, so the foot doesn't scuff or jolt at lift-off and touch-down. The curve overshoots `±amp` by a few percent, more in faster gaits (tripod ≈ 9% of amp at each end). amp = r·(stride ∓ turn) (left/right). The ramp r rises over the first cycle, so the legs that step last aren't dragged too far back. On stop it falls over one step; then each leg not within 3 steps of centre takes one more step, to centre. The settle check runs before a leg can start a swing, so a leg already at centre doesn't step in place. A leg that starts inside its swing window waits for its next one (state 2). A key (tty only), `cycles` or `secs` (walk's last argument, 0 = no limit; only the tip walk uses it) starts the graceful stop; ctrl-c (SIGINT handler, only during `walk`) freezes the pose and returns to the prompt. Each tick reads one servo's load, round robin (a 2-byte read after the sync write; ticks stay about 20 ms), and the walk ends with a per-servo peak load report. Those reads also note status errors, which print after the command. It starts with `stand(1000)` unless its last argument, `quick`, is set and it is already `standing` at the height it stood at (`stood_height`: `set height` doesn't move the legs, so a quick start after it would jump them); then it only runs `check_servos()` and goes (the tip walk; a `move` by hand since the stand isn't noticed). Nothing is drawn during a walk, so the face holds still (no blinks) until it ends. The walk prints its longest tick and how many were over 25 ms. Drawing the face from the walk loop was tried on 2026-10-06 (so it could turn to a new front as a tip walk set off) and taken out the same day for the user's simpler idea (turn it during the lift, see Tipped). What it showed: with the draw on one tick and the 7 ms send on the next, a tip walk had 44 of 362 ticks late (36 ms) because the draw took 34 ms; with the divisions out of the pixel loop (see The face) the draw took 17 ms and no tick was late, but 17 ms plus the bus traffic is the whole of a 20 ms tick, so there was no margin. A late tick only delays one pose (the gait runs on real time), and the user saw nothing wrong either way.
- **`calibrate`:** stands, then evens out the load on the six lifts by nudging their offsets, starting from the current ones (some feet were off the ground at 511, so they would be hard to find from zero). Each round reads every lift's load 5 times (signed by `lift_dir`, + = foot pushing down), and moves a lift above the mean up and one below down by `dev/30` steps, 1–2, then `send_pose(200)`. It stops when all are within `CAL_TOL` (15 = 1.5%) of the mean, or after `CAL_ROUNDS` (20), keeping the round with the smallest spread. Each offset can move at most `CAL_MAX` (30) from where it started, and it refuses if the mean load is under 2% (robot held up). The SC09 reads load 0 inside its dead zone, so a foot that touches lightly reads the same as one in the air, and above it in steps of 15 (1.5%), one per step of position error; `CAL_TOL` is one such step. The first run took 6 rounds, from 0–12% to 6–7.5% on every lift, with the lifts' total offset almost unchanged (-40 to -43), so the body height barely moved. `offset[]` isn't const: `calibrate` and `offset [id val]` change it until exit and print it as C (`print_offsets()`), for pasting into the source. Do it again whenever the weight moves (e.g. the battery lead: it was off to one side until 2026-10-01).
- **`ident [id]`:** twitches each id (default 1-12) in turn, 1 s apart, +30 from its present position and back (raw, no offset; up for a lift), printing what `legs[]` says the id is. For finding mixed-up ids.
- **`check_servos()`:** `walk`, `legtest` and `stand` first read voltage/temp from all 12 servos and refuse if any don't reply, since sync writes get no replies. It prints any status errors (e.g. overload) straight away rather than after the command.
- **Screen and `selftest`:** the I/O section's `scr_init`/`scr_clear`/`scr_text`/`scr_show` (stubs on the Pi) (and `scr_pixel`) drive the ATOM's 128×128 panel over SPI (MOSI G21, SCLK G15, CS G14, DC G42, RST G48) from a frame buffer, sent whole. The panel is a GC9107 or, on some batches, an ST7735S, told apart by RDDID; init sequences, offsets and the ID probe are from M5GFX (`src/M5GFX.cpp`, board_M5AtomS3R). This ATOM's is an ST7735S (id 0f7683). The backlight is an LP5562 at 0x30 on the internal I2C (SDA G45, SCL G0, shared with the IMU; Port A is a separate bus). The font is Adafruit's 5×7 glcdfont (BSD, notice kept); log lines are at scale 2, so 10 characters by 8 lines. `selftest()` runs at startup on both hosts and by command, reads only, and logs each check through `t_line()` (console line, plus a short screen line on the ATOM, 250 ms apart); then the eyes come up (see Alive).
- **`loads [secs]`** streams each servo's load and position error (one 20-byte read from 0x2A per servo, about 80 sweeps of 12 a second; signed by `hip_dir`/`lift_dir`), with the seconds on the ATOM's screen. Tried 2026-10-05 for using the servos as touch sensors (press an edge, the body bows that way). Findings (with the lifts at I 0, as they were then): every servo has dead zone 1, P 15, D 15, I 0 (0x15–0x17). With no I term a lift only drives in proportion to its error, so standing it sags 2–4 steps under the body (load reads 0 in the dead zone, then about 60/75/90 at 2/3/4 steps) and gear friction holds it wherever it ends up: a press that does move a foot leaves it there (it doesn't spring back), and a firm press on the front edge moved the feet only 0–1 step (the RF hip about 3). A few single samples read 5–10 steps off and are noise, so filter. Retried with the lifts at I 1 (2026-10-05, a firm press between legs 1 and 2, just after a walk): lifts 9 and 10 (legs 3 and 4) dropped from about 13% to 8% and their errors from 4–5 to 1–2 steps, lifts 7 and 8 barely changed, and nothing came back after the release, so I 1 doesn't make presses usable either; left for now, with tipping (see Tipped) as the way to interact. Also seen then: just after a walk the lifts stood 1–5 steps off goal with loads of 5–14%, even with I 1 (the standing checks right after a stand saw 0–2 steps). So stock servos make poor touch sensors; options not yet tried: a softer P on the lifts (bigger deflections, but more sag, and calibrate and walking change), or the IMU (the gyro should see the rocking of a press; the BMI270 needs Bosch's 8 KB config blob loaded at init).
- **IMU:** a BMI270 at 0x68 on the internal I2C with the backlight (`sys_i2c_dev()` sets the bus up once). `imu_init()` soft-resets it, uploads Bosch's 8 KB config file (`atom/bmi270_config.h`, from BMI270_SensorAPI v2.86.1, BSD-3, the only other file the ATOM build includes) in 256-byte chunks, waits for INTERNAL_STATUS = 1, then sets accelerometer ±4 g at 100 Hz and gyro ±500 °/s at 200 Hz. The waits after the soft reset and PWR_CONF need to be real (5 ms each): with 1 ms ticks a `msleep(1)` can be almost nothing, and the upload then fails with init_err (status 2). The magnetometer (BMM150, behind the BMI270's aux interface) isn't set up. `imu_read()` rotates the chip's readings by `IMU_YAW` (−150°) into the robot's axes: +x towards the gap between legs 1 and 2, +y 90° anticlockwise from that seen from above, +z up. Found on 2026-10-05 with the ATOM in the new cage, lying flat on the leg 1–4 axis (chip +x at leg 4), by tipping the robot up at each gap in turn: the six tilts were 60° apart within ±10°, going clockwise. A couple of cm of lift is 6–20°, against 0.1° of noise, with the gyro at 8–25 °/s; setting it down jolts the accelerometer to about 1.15 g. At rest it reads a few degrees off level: about 1.7° of that turned with the robot when it was turned round on the desk (before the cage), so it's the robot's own (body on its legs, mounting, chip offset), the rest the desk. `imu [secs]` streams it; `selftest` reports pitch and roll.
- **Leg numbering:** legs 1–6 (hip ids) go clockwise round the body seen from above, so 1 and 4 are opposite (the user's numbering, confirmed with the IMU on 2026-10-05). The walk goes towards the gap between 6 and 1 (`legtest 1` swings leg 1's foot towards leg 6), so 1, 2, 3 are the right side front to back (RF, RM, RR) and 6, 5, 4 the left (LF, LM, LR). Until 2026-10-05 `legs[]` had an older wiring: 1–3 left and 4–6 right, both front to back, so the sides were swapped (turning was reversed and the leg names wrong) and 4 and 6 were each other's rows. `hip_dir` didn't change: a higher position turns every hip clockwise seen from above, so it's −1 for 1–3 and +1 for 4–6. The tripod groups are the same either way (1, 3, 5 and 2, 4, 6). The user doesn't think of the robot as having a front; the walk's is just where it goes.
- **Tipped** (`tips()` and `tip_walk()`, from `alive()`): lift it at an edge and put it down, and it walks away from that edge (away from whoever lifted it) for `TIP_WALK_S` 5 seconds, fixed for now. Since 2026-10-06 this is the only way it reacts to being handled: until then a tip made it bow towards the lifted edge (`bow_to()`: the two legs either side to 700, hold, stand; before that the `bow [secs]` command), and a slide made it walk (`push_to()`); both were taken out, with the safety checks (below), as too much too soon and erratic (the user: simplify and go slower). While `standing`, level is the IMU's reading averaged over `TIP_LEVEL_MS` 300 (`imu_level()`), taken again after every command (`tips_relevel`, set by `edit_line()`) and every tip walk. A tilt from level of over `TIP_ON` 3° is a tip; the direction at the biggest tilt is kept (`pang`, pointing at the lifted edge), counting only samples within `TIP_STILL` 0.05 g of level's total (putting it down jolts the accelerometer to 1.1–1.16 g, in any direction, bigger than the tilt), and once it has been under `TIP_OFF` 1.5° for `TIP_SETTLE_MS` 300 (put down and still) `tip_walk()` makes the gap nearest `pang` + 180° (`tip_gap()`) the front (`set_front`) and calls `walk(0, stride, 0, TIP_WALK_S, 1)`: the current gait and stride, no turn, a quick start (no stand first, see `walk()`), the graceful stop beginning after 5 s, so it is on the move for a step or two longer. From put-down to the first step is the 300 ms settle plus `check_servos()` (12 short reads), against about 2.2 s before (a 0.7 s wait for the face, then the walk's 1.2 s stand): the user wanted 500 ms at most, as it walks away from the hands. **The face turns during the lift** (the user's idea, in place of drawing it while walking): as soon as a lift passes the tip tests (peak over 3°, rotation at least half of it, held 250 ms) `tips()` sets the front to `tip_gap(pang)`, while the robot is still in the hand, so the idle loop's `eyes()` turns the face there (at `FACE_TURN` 0.3 of what's left per frame, about 0.3 s for most of a half turn) and it shows where it will go; `front0` puts the front back if the event ends as not a tip. At put-down `tip_walk()` sets `face_snap` and calls `eyes()` once, which finishes any turn still under way in one frame, since nothing draws during the walk (before this the face stopped part-way and finished after the walk). Tried on the robot on 2026-10-06: the user finds it a far better experience ("you know the lift is sufficient because the face turns"); tips of 8.9° and 11.4° walked away from the lifted edge (lifted at −180°: gap 1; at 8°: gap 4), a 4.2° jolt of 22 ms was ignored, and every walk reported 0 of 362 ticks late. Sliding it along the desk reads as a tilt too (the accelerometer can't tell acceleration from tilt), so a tip also needs the gyro's rotation about horizontal axes, added up to the moment of the biggest tilt, to be at least `TIP_ROT` (half) of that tilt, and the tilt held over 3° for `TIP_HELD_MS` 250; anything else prints "not a tip … (slid?)" and does nothing. Measured 2026-10-05: pushes and pulls read 3–11° of "tilt" for 0.2–0.55 s but rotated it only 0.3–1.3°; tips of 14° were taken as tips. (A peak gyro rate test didn't work: a slide's stop jolt rocks it at up to 11°/s.) Gravity off z (under 0.5 g) for a second while standing is "knocked over": it sits. The tip detection was tested on 2026-10-05 as the bow's trigger in all six directions (a small tilt is sometimes a leg off); the walk in its place went on the robot on 2026-10-06 and the user reports it working. The user's bow by hand, if it comes back: `stand; move 7-8 700 1000; stand` (the body is designed to come down on a bowed edge safely). The electronics sit in a separate hex cage on top (the robot looks like a phage).
- **`sit [ms]`:** the user's switch-off pose (`move 7-12 1000 1000`): every lift to `SIT_POS` 1000 plus its offset, capped at 1003, hips untouched, sent with `sync_move()` directly as it's past `UP_MAX`. All 12 servos have angle limits 20..1003 (0x09/0x0B), so a goal above 1003 is clamped by the servo: lift 11 (offset +9) stopping at 1001 looked like it falling short, but it was on its clamped goal. The body sits on the ground and the legs point up inside it, safely, with no load on the servos. It sets each leg's z to match, though nothing reads it before the next `stand`.
- **Startup and `selftest`:** the self test is in two halves. `t_pre()` is the go/no-go for standing (screen and IMU answer, servos reply, battery, temperatures, error bits, overload settings, gains, positions); `t_standing()` needs the weight on the feet: each lift's goal, position, load and voltage in one 21-byte read from 0x2A, 5 times, giving the load on each foot (signed as in `calibrate`; warns over `FEET_SPREAD` 5% from the mean, or if the mean is under 2%: held up), sag (`lift_dir` × (position − goal), + = the foot pushed up by the weight; 2–4 is usual, warns over `SAG_MAX` 6), level (IMU, warns over `LEVEL_MAX` 5°), the highest load on any servo, and the battery under load. `t_end()` prints the result and leaves the log up a second; then the eyes take over, their whites coloured by `t_worst` (white, yellow, red) with the first problem (`t_bad[0]`) under them, nothing if all's well. At power-on the ATOM runs `t_boot(1)`: `t_pre()`, then unless something failed `stand(1000)` and `t_standing()`, then `t_end()`; the Pi runs `t_boot(0)`, without standing. The `selftest` command runs `t_standing()` only if `standing` is set: `stand()` sets it, `sit()` and a walk frozen by ctrl-c clear it (other commands, `move` and so on, don't touch it). Opening the ATOM's USB port resets it, even with DTR and RTS held false, so connecting makes it stand up; the user is fine with that for now. **Foot loads and the I gain:** with the lifts at I 0 (before 2026-10-05), standing loads read only 0, 6, 7.5, 9% (one value per step a foot is pushed up), each stand left a different foot or two at 0, and `calibrate` couldn't settle (18 rounds of 1-step nudges just moved which feet read 0): it was measuring how the feet landed, not the offsets. With I 1 on the lifts (see Gains) they stand within about 1.5% every time, so the feet check is back at 5% (3% fired on boots at 3.1–3.9%) and `calibrate` means something again. `t_standing()` waits 1 s after a stand first, for the I term to take up the weight (read at 0.2 s, two of four stands were still uneven). The IMU's tilt was steady through all of it (3.0–4.0°), about 1.7° of it the robot's own.
- **Alive (the idle loop):** the REPL used to block on input; now `edit_line()` waits with `con_getc_ms(ALIVE_MS)` (20 ms; −2 = no key; the ESP side reads the USB-Serial/JTAG with a timeout, the POSIX side `select()`s) and calls `alive()` each time nothing came. Commands run as before and the loop pauses while one does; `eyes_dirty` makes the eyes redraw after a command that used the screen. Single-threaded, so nothing else talks on the bus. Done: the face, the servo watch, tipped (lift an edge and it walks away for 5 s; with knocked over: it sits) and facing (a tip sets the walk's front and the face turns to it) (all below). Taken out on 2026-10-06: bowing, pushed (a slide made it walk that way) and the safety checks. Not done: picked up (all six feet unloaded). It only moves by itself in reaction to being handled or to protect itself. The user's view: make it fun by doing what's asked of it, without adding lidar and so on, and keep it easy to add input devices.
- **Servo watch:** `watch()`, from `alive()`: one 4-byte read from 0x3C (load, voltage, temperature, plus the reply's error bits) per tick with a 10 ms timeout, round robin, so each servo about every 0.25 s; after each sweep it judges the worst problem. It prints a problem once per kind (a battery voltage or temperature that drifts by 0.1 isn't a new one) and keeps the screen's numbers up to date quietly. Serious (whites red; it `sit`s if `standing`): no reply 3 reads running (`no N`; `no servos` if all, which only happens on USB power with the battery off, or the ATOM–adapter link broken, since the battery now powers the ATOM too), overload or overheat bits, 65 °C, a load over 60% held 2 s (protection cuts in at 80% for 4 s), battery under 6.6 V. Warnings (yellow): 55 °C, other error bits, battery under 7.0 V (with 0.2 V of hysteresis). The battery minimum only counts servos whose last read replied: a servo's stored voltage is 0 until its first reply, and one missed 10 ms read on the first sweep after boot used to read as "battery flat: 0.0 V" and sit it down. It prints a line when a problem starts or clears (clearing the half-typed line and redrawing it) and the eyes show it; the self test's result shows for 15 s after it (`t_shown`), then the watch's. Off USB the console goes nowhere, so the eyes are the only place a warning shows. Tested 2026-10-05 only to stay quiet when all's well; the warning paths weren't provoked (the user was happy to skip pulling a cable).
- **The face** (for the user's grandchild George, in place of "Hi!"): `eyes()`, drawn only when something changed, every pixel turned back into the face's own frame (rotation `beta`) and drawn from there with `scr_pixel`, so it can face any way and stays inside the screen's inner circle. Two almond-shaped eyes (two parabolas meeting at the corners: `EYE_RX` 30 across, `EYE_UP` 25 above their centre, `EYE_DOWN` 19 below, centres at ±`EYE_X` 31, `EYE_Y` −8), a blue iris (`IRIS_R` 17, `IRIS_COLOUR`) and pupil (`PUPIL_R` 8) clipped to the whites, a highlight that stays put, and a mouth (a parabola `MOUTH_W` 22 either side, `MOUTH_T` 4 thick, corners at `MOUTH_Y` 25). The face turns so its mouth points at the walk's front (`MOUTH_AT_FRONT`; someone standing there sees it upright, looking at them): when `front` changes it turns there over about half a second, the short way round (`FACE_TURN` 0.3 of what's left each frame; `face_snap` makes the next `eyes()` finish it at once, for the tip walk). A frame is a 17 ms draw (measured on the ATOM, 2026-10-06) plus 7 ms to send. The draw was 34 ms until the divisions came out of the pixel loop: the ESP32-S3 has no float divide, and the loop called `__divsf3` twice and `__truncdfsf2` once per pixel over most of the screen (found by disassembling `eyes` in `atom/build/.../hector.c.obj` with `xtensa-esp32s3-elf-objdump -dr`). It now multiplies by constant reciprocals, takes `mood` and the lid as floats before the loop, and skips the eye and mouth tests outside their rows in the face's frame; compared with the old loop on the Pi over 36000 frames, 17 differed, by one pixel each. The screen's top points at leg 1 (+30° in `imu_read()`'s axes: text is upright read from the ATOM's USB side, and leg 1 is then straight ahead), so its right is at −60°. A blink brings the lid down from the top and back in 180 ms, every 2–6 s, one in five followed by a second; a glance to a random point lasts 0.6–1.8 s every 4–10 s; the irises ease towards it (up to `LOOK_X` 10 px across, `LOOK_Y` 4). The status shows in the whites (white, yellow, red), the text along the bottom (upright, on a black strip) and the mouth: `mood` eases to +1 (smile) when all's well, 0 (flat) for a warning, −1 (frown) for a failure. Its shape went from round to wide to almond, and the head turning was George's idea (and the user's wife's: "rotate the little square"); dimples at the mouth's corners were tried and dropped (not enough pixels).
- **Pushed (removed 2026-10-06):** a slide along the desk used to start a walk that way (`push_to()`, in git up to 76cf807): an event that rotated under 30% of its "tilt", of at least 5°, was a push, and its way and distance came from adding up the last 2.5 s of horizontal acceleration twice. On the robot it was erratic (some walks went the wrong way; distances were ±50%), so it's gone and a slide does nothing. What was learnt, if it's tried again: a slide of 3–15 cm is a smooth push of about 0.1 g for 0.3–0.5 s in the direction of travel, then a sharper stop of 0.13–0.45 g the other way; a gentle push only crosses 3° at its stop, which points back, so the first jolt gives the wrong way; integrating from 400 ms before the event, with a 0.015 g dead band, got 8 of 9 recorded slides within 15°.
- **Safety (removed 2026-10-06; revisit before the robot goes to the grandchildren):** there is now nothing between a tip and the walk except the 0.3 s settle and the servo check (by the user's choice: it walks away from the hands), and nothing stops a walk but a key, ctrl-c, its time or the servo watch afterwards. What was there (git 461de9d and 76cf807) and why it went: `hands_off()` waited for 1.5 s of stillness after a tip or push before moving (cancelling if touched), and `walk` went limp (`go_limp()`: torque off on all twelve with one broadcast write, a sleepy face with "limp") on a servo over 50% load, no lift over 3% for two rounds of reads (picked up), or the IMU over 120°/s or 1 g. Together with push-to-walk it made the robot erratic. Measurements worth keeping for the next try: normal tripod walks (default settings) read 36–42°/s and 0.20–0.30 g, once 56–65°/s and 0.54–0.55 g, so limits of 60°/s and 0.5 g stopped a normal walk; a gentle pick-up neither turns nor jolts the IMU, hence the load test, which was never confirmed on the robot. The SC09s honour a broadcast torque write (checked 2026-10-05); `stand` still turns torque on that way first.
- **Front** (`front [1-6]`, `set_front()`): any of the six gaps can be the walk's front, as the legs are 60° apart and all fitted the same way. Gap k is between legs k and k+1 (6 and 1 for gap 6), at −60(k−1)° (`gap_ang()`). Going clockwise from the front gap, the next three legs are the right side front to back, and the other three, anticlockwise, the left; `hip_dir` is −1 on the right and +1 on the left (a higher position turns every hip clockwise). `legs[]` as written is gap 6, and `set_front(6)` reproduces it exactly (checked). A tip sets the front to the gap opposite the lifted edge (it walks away from whoever lifted it), and the face turns that way. It's gap 6 again after a reset.
- **`set`:** the `params[]` table (gait, step, stride, lift, height) with ranges. The defaults are tripod (the user's choice, 2026-10-05: a little faster) with the gentle first-walk settings otherwise (step 800, stride 50, lift 70, height 0), put back on 2026-09-26 while the user retunes for the new body; keep them until the user gives new values. The user's tuning on the old body was tripod, step 1000, stride 100, lift 100, height -60 (a slow, low, splayed walk that looked natural).

## Future ideas (not started)

- **Startup calibration:** keep the table from a deliberate `calibrate` on a flat desk, saved to flash, as the reference. At startup, run `calibrate` from it with a tight cap (about ±8 steps instead of `CAL_MAX` 30) and use the result for that session only. If a leg hits the cap or it doesn't settle, fall back to the saved values and warn: that means a sagging servo (like the old servo 9), a loose horn, uneven ground or the robot being held. Startup corrections that grow over weeks would show servo wear. Offsets depend on `height`, so calibrate at the walking height or keep a set per height. Later, the same load readings could level each foot as it lands while walking.
- **The ATOM's screen** (0.85", 128×128, colour) as a status page: the startup check result (OK, or which leg hit its cap); six load bars laid out like the legs, standing or walking; battery from the servos' voltage register (2S is low at about 7.0 V); overload/overheat warnings by id and leg; the gait, stride and step, and whether it's walking. The gait code keeps its I/O in `send_pose()`/`send_leg()`, so the screen only needs to read the state it already has.
