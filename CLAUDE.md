# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Hector, a small hexapod: 6 legs, 2 DOF each, 12 Waveshare SC09 bus servos. `hector.c` is a single-file C REPL that started as a copy of `../servo/servo.c` (the generic SC09 tester, https://github.com/op12no2/servo) and keeps all its commands; the hexapod commands (`stand`, `legtest`, `ident`, `offset`, `calibrate`, `walk`, `set`) are in the `/* ---- hexapod ---- */` section. The same file builds for the ATOM S3R: `atom/` is an ESP-IDF project whose only source is `../hector.c`, and the I/O section near the top (`/* ---- I/O ---- */`) has an `ESP_PLATFORM` half and a POSIX half; nothing else differs, so keep it that way. Fixes to the servo layer (protocol, `move`, the line editor) likely belong in `../servo` too. Its `CLAUDE.md` has the details of the SC09 and the adapter: register behaviour, move overshoot, the unreliable moving flag, the dead zone and so on. There are no tests and no dependencies beyond libm.

## Hardware

- **Host:** either the Raspberry Pi 5 (where Claude Code runs) via the Waveshare Bus Servo Adapter (A) over USB (stable path `/dev/serial/by-id/usb-1a86_USB_Single_Serial_*`), jumper in B, or the ATOM S3R (the on-board controller) via the adapter's UART header, jumper in A; 1 Mbps either way. The ATOM's USB is its console and flashing port, `/dev/serial/by-id/usb-Espressif_USB_JTAG_serial_debug_unit_*`. Both enumerate as `/dev/ttyACMn`, so use the by-id paths (`./hector`'s default `/dev/ttyACM0` may be the ATOM). The gait code has no I/O of its own besides `send_pose()` and `send_leg()`.
- **ATOM wiring** (`wiring.md`, `wiring.svg`; built 2026-10-02 with patch leads, D1 still on order, so the buck's 5V lead to the ATOM is unplugged and the ATOM runs from USB; reconnect it once D1 is in, and never with USB and the battery both on without D1): ATOM G38 (TX) / G39 (RX) / GND to the adapter's 3-pin UART header H2 (GND, RXD, TXD, named for the host: RXD to RX, TXD to TX), jumper in A (B = the adapter's USB, for the Pi); `BUS_TX`/`BUS_RX` in `hector.c`. The adapter's UART side is 3.3 V (LVC buffers), so no level shifting. Power: battery through the MPM3610 5 V buck and a Schottky into the ATOM's 5V pin, which is the same net as its USB VBUS (so the diode stops the buck and a USB port back-feeding each other). The adapter's own 5 V/3.3 V aren't brought out. G39, G38, 5V, GND are the ATOM's right-hand header in that order; Port A (G2 SDA, G1 SCL) is kept for the sensor.
- **Servos:** SC09, 300° over 0..1023 (0.293°/step), 2.3 kg·cm. Supply is a 2S LiPo straight to the servos (rated 4.8–8.4 V).
- **Geometry:** `cad/README.md` has the parts, how they fit together, the foot position and body height against `height`, and clearances measured in CAD. Since 2026-09-26 the body is a 220 mm disc with a central wiring cage, the hips are 90 mm from the centre, and the legs reach 91.5 mm from the lift axis. The parts share one coordinate frame; `05_one_hip_assembly.step` has the body, lid and one leg's parts as named components, which is the easiest to measure. To measure the STEP files, `pip install cadquery-ocp` (Open CASCADE; aarch64 wheels exist) into a venv. Its OCP 8 API needs `Bnd_Box.CornerMin/CornerMax`, not `Get()`, `TopoDS.Face`/`Vertex`/`Edge`, not `Face_s` etc., and `OCP.OCP.collections.Sequence_TDF_Label` for a `TDF_LabelSequence` (read the assembly with `STEPCAFControl_Reader` and `XCAFDoc_DocumentTool.ShapeTool_s`). All-up weight was about 500 g with the old 164 mm body; the new body and lid are about 50 cm³ more plastic, not yet weighed.
- **Legs:** hip (yaw) servos are ids 1–6, lift servos 7–12; leg n = hip n + lift n+6. Nominal (stand) position is 511 for all, plus `offset[]` (below). Lifts can go up to the servo limit but only about 50 steps below 511 before the leg hits the chassis (the user judges 50 itself OK); `DOWN_MAX` (50) clamps that in `send_pose()`. That was on the old body; in CAD the new one has the same margin as the old (the leg meets the plate's outer ring), so 50 should still hold, but it hasn't been checked on the robot. `height` runs from -`SPLAY_MAX` (-150: stance legs 150 above centre, body lower, legs splayed) to `DOWN_MAX`. Hips can easily do 300 either way; `HIP_MAX` (150) clamps them, as neighbouring legs can meet. In CAD, though, turning a hip towards the side its leg plate is on (the same rotation for every hip, as all six legs are fitted the same way round: forward on one side, back on the other) brings the leg's lower half against the plate's outer ring, sooner the lower the foot: about 123 steps at `height` 0, 61 at +50, 177 at −60. A walk's hip swing is up to stride + turn, plus the swing curve's overshoot (≈9% in tripod).
- **Overload protection** (Waveshare's SCS memory table, https://files.waveshare.com/upload/5/5c/SCS_Series_Memory_Table_Analysis.xls; the SC09s here hold its defaults): if a servo's load (0x3C, the drive duty cycle in 0.1%) stays over the overload torque (0x27, 80%) for the protection time (0x26, 100 × 40 ms = 4 s), its output drops to the protection torque (0x25, 20%) and its status reports overload (bit 5). Unloading conditions (0x13) = 0x20, i.e. only overload protection enabled. A lift servo is loaded all the time its foot is down, so standing still and slow gaits (a wave stance at an 800 ms step is 4.0 s) are the risk, more than fast ones.
- **Gains:** every servo came with P 15, D 15, I 0 (0x15–0x17, EPROM). On 2026-10-05 the six lifts were set to **I 1** (`lock 7-12 0; wb 7-12 0x17 1; lock 7-12 1`): with I 0 a lift only drives in proportion to its error, so it holds the body 1–4 steps off its goal, friction leaves it wherever it lands, and its load reads only 0 (dead zone), 6, 7.5, 9%; with I 1 it pushes its foot onto its goal (error 0–2) and its load is the force on that foot, in finer steps. Standing loads then came out within 1.0–1.4% of each other on every stand (four sit/stand cycles, nearly identical), and `calibrate` balanced in one round with no offset change. The hips are still I 0. The self test checks the gains (`P_GAIN`, `D_GAIN`, `I_HIP`, `I_LIFT`), so a replaced servo with factory settings gets flagged with the commands to fix it. Walking compared on 2026-10-05 (default wave, `walk 2` forward and `walk 2 -50` back, each with I 1 and then I 0): the peak loads were the same within run-to-run noise, all under 26%; lifts 8 and 12 (legs 2 and 6) peaked at 22–26% in every run against 9–17% for the rest, either setting. The user couldn't see any difference either, so the lifts stay at I 1. To go back: `lock 7-12 0; wb 7-12 0x17 0; lock 7-12 1`.
- **Servo 9** (the lift of leg 3, LR) was replaced on 2026-10-01 (the old one went into overload protection and sagged). The new one replies as id 9 and holds the default overload settings.
- **Offsets:** `offset[]` (per id) is added to every goal position sent, by `move` and by `leg_goals()`, so with `[7] = 20`, `move 7 511` sends 531. At 511, the RF and RR feet (lifts 10 and 12) were off the ground; the user set them to -20, then `calibrate` (2026-10-01, height 0, battery lead centred) gave 7:+4 8:-8 9:+3 10:-21 11:+3 12:-24; rerun on 2026-10-05 (on the ATOM, height 0) from those, it balanced in 3 rounds (spread 7% → 1%, mean 8%) at 7:+4 8:-7 9:+3 10:-23 11:+5 12:-25, and again the same day after the electronics cage went on top (battery freshly charged, 8.1–8.6 V) in 4 rounds (0–16.5% → 9–10.5%) at 7:+4 8:-7 9:+2 10:-26 11:+9 12:-25. A foot that is high needs a negative lift offset. As `DOWN_MAX` applies before the offset, lifts 10 and 12 can go about 20 steps further down than the others; fine if the offset makes up for a horn set off true (the chassis contact moves with it), not checked. Reads (`pos`, `stat`, `verify_move()`) are raw servo positions; `ww` to 0x2A doesn't add it.
- **Layout and directions:** `legs[]` (layout, `hip_dir`, `lift_dir`) as first written walked the robot correctly without changes, so the guesses were right; the layout was redone on 2026-10-05 for the current numbering (see Leg numbering). If a leg is rebuilt, check its directions before walking: a wrong `lift_dir` would drive the swing legs down into the chassis. `legtest` lifts to 700 (189 above centre), well past the 50-step chassis margin if `lift_dir` is wrong, so on a rebuilt leg check the lift direction with a small `move` first.

## Build / run

```
make                               # cc -O2 -Wall -Wextra -o hector hector.c -lm
./hector [/dev/ttyACM0] [baud]     # defaults: /dev/ttyACM0, 1000000
echo "walk 2" | ./hector           # non-tty stdin works for scripted commands

cd atom && source ~/esp/esp-idf/export.sh   # the ATOM build (ESP-IDF v6.x at ~/esp/esp-idf)
idf.py build && idf.py -p /dev/serial/by-id/usb-Espressif_* flash
```

To script the ATOM's REPL (it has no non-tty mode: it always line-edits and echoes), open its port with DTR and RTS both false before opening (pyserial: set `s.dtr = s.rts = False`, then `s.open()`), or the chip resets, and end lines with `\r\n` or `\r`. The IDF venv (`~/.espressif/python_env/*/bin/python`) has pyserial.

Keep the build warning-free under `-Wall -Wextra`. Walking can only really be verified on the robot; if you can't test on it, say so. Never make it move unless the user is there: it can walk off the desk.

## Architecture (hexapod section)

- **I/O (`/* ---- I/O ---- */`):** the bus (`open_port`, `bus_flush`, `bus_write`, `read_bytes`), the console (`con_init`, `con_tty`, `con_raw(block)`, `con_restore`, `con_getc`, `con_drop`), ctrl-c (`sigint_catch`/`sigint_restore`, `halted`), `msleep` and walk's fixed-rate ticks (`tick_start`, `tick_wait`). On the ATOM the bus is UART1 (TX G38, RX G39, a pull-up on RX) and the console the USB-Serial/JTAG driver: no termios and no SIGINT, so `con_tty()` is always 1 and ctrl-c arrives as byte 3, which `walk` checks for (`idf.py monitor` passes it through). There is no TX echo over H2, unlike some USB adapters (`txrx` handles either). `sdkconfig.defaults` sets 1 ms FreeRTOS ticks (bus timeouts are a few ms) and a 16 KB main task stack (`move`/`verify_move` keep several `int[254]` on the stack). With no USB host, console output is dropped rather than blocking. The line editor treats CR LF as one enter, as `idf.py monitor` sends both.
- **`legs[]`:** per leg, side (0 left, 1 right) and row (0 front, 1 middle, 2 rear), hip and lift ids, `hip_dir` (+1 if a higher position swings the foot forward), `lift_dir` (+1 if a higher position raises the foot), and the current state `x` (hip, + forward) and `z` (lift, + up from the stance pose), in servo steps.
- **`send_pose(tm)`:** turns every leg's x/z into 12 goal positions (applying dir, `height`, the clamps and `offset[]`) and sends them as one `SYNC_WRITE` (`sync_move()`, which takes a position per id) with goal time tm. It and `send_leg()` (one leg's two servos, for `legtest`, which leaves the other legs where they are) are the only things that command the legs; both go through `leg_goals()`.
- **`gaits[]`:** a gait is the fraction of the cycle each leg is in the air (`swing`) and each leg's offset in the cycle, indexed by [side][row]: wave (one leg at a time, back to front, right side then left), ripple (two), tripod (three).
- **`walk()`:** streams a pose every `TICK_MS` (20 ms, goal time 20). Global phase advances by dt/period (period = `step` / `swing`). On the ground a leg's hip sweeps back at 2·amp per stance time. That rate is the same for every foot on the ground, so no foot slips. In its swing window a leg lifts (z = lift·sin πw) and its hip follows a cubic (Hermite) from its lift-off x to `amp`, starting and ending at the ground rate, so the foot doesn't scuff or jolt at lift-off and touch-down. The curve overshoots `±amp` by a few percent, more in faster gaits (tripod ≈ 9% of amp at each end). amp = r·(stride ∓ turn) (left/right). The ramp r rises over the first cycle, so the legs that step last aren't dragged too far back. On stop it falls over one step; then each leg not within 3 steps of centre takes one more step, to centre. The settle check runs before a leg can start a swing, so a leg already at centre doesn't step in place. A leg that starts inside its swing window waits for its next one (state 2). A key (tty only) or `cycles` starts the graceful stop; ctrl-c (SIGINT handler, only during `walk`) freezes the pose and returns to the prompt. Each tick reads one servo's load, round robin (a 2-byte read after the sync write; ticks stay about 20 ms), and the walk ends with a per-servo peak load report. Those reads also note status errors, which print after the command.
- **`calibrate`:** stands, then evens out the load on the six lifts by nudging their offsets, starting from the current ones (some feet were off the ground at 511, so they would be hard to find from zero). Each round reads every lift's load 5 times (signed by `lift_dir`, + = foot pushing down), and moves a lift above the mean up and one below down by `dev/30` steps, 1–2, then `send_pose(200)`. It stops when all are within `CAL_TOL` (15 = 1.5%) of the mean, or after `CAL_ROUNDS` (20), keeping the round with the smallest spread. Each offset can move at most `CAL_MAX` (30) from where it started, and it refuses if the mean load is under 2% (robot held up). The SC09 reads load 0 inside its dead zone, so a foot that touches lightly reads the same as one in the air, and above it in steps of 15 (1.5%), one per step of position error; `CAL_TOL` is one such step. The first run took 6 rounds, from 0–12% to 6–7.5% on every lift, with the lifts' total offset almost unchanged (-40 to -43), so the body height barely moved. `offset[]` isn't const: `calibrate` and `offset [id val]` change it until exit and print it as C (`print_offsets()`), for pasting into the source. Do it again whenever the weight moves (e.g. the battery lead: it was off to one side until 2026-10-01).
- **`ident [id]`:** twitches each id (default 1-12) in turn, 1 s apart, +30 from its present position and back (raw, no offset; up for a lift), printing what `legs[]` says the id is. For finding mixed-up ids.
- **`check_servos()`:** `walk`, `legtest` and `stand` first read voltage/temp from all 12 servos and refuse if any don't reply, since sync writes get no replies. It prints any status errors (e.g. overload) straight away rather than after the command.
- **Screen and `selftest`:** the I/O section's `scr_init`/`scr_clear`/`scr_text`/`scr_show` (stubs on the Pi) drive the ATOM's 128×128 panel over SPI (MOSI G21, SCLK G15, CS G14, DC G42, RST G48) from a frame buffer, sent whole. The panel is a GC9107 or, on some batches, an ST7735S, told apart by RDDID; init sequences, offsets and the ID probe are from M5GFX (`src/M5GFX.cpp`, board_M5AtomS3R). This ATOM's is an ST7735S (id 0f7683). The backlight is an LP5562 at 0x30 on the internal I2C (SDA G45, SCL G0, shared with the IMU; Port A is a separate bus). The font is Adafruit's 5×7 glcdfont (BSD, notice kept); log lines are at scale 2, so 10 characters by 8 lines. `selftest()` runs at startup on both hosts and by command, reads only, and logs each check through `t_line()` (console line, plus a short screen line on the ATOM, 250 ms apart), then shows Hi! coloured by the worst result, with up to four problem lines under it.
- **`loads [secs]`** streams each servo's load and position error (one 20-byte read from 0x2A per servo, about 80 sweeps of 12 a second; signed by `hip_dir`/`lift_dir`), with the seconds on the ATOM's screen. Tried 2026-10-05 for using the servos as touch sensors (press an edge, the body bows that way). Findings (with the lifts at I 0, as they were then): every servo has dead zone 1, P 15, D 15, I 0 (0x15–0x17). With no I term a lift only drives in proportion to its error, so standing it sags 2–4 steps under the body (load reads 0 in the dead zone, then about 60/75/90 at 2/3/4 steps) and gear friction holds it wherever it ends up: a press that does move a foot leaves it there (it doesn't spring back), and a firm press on the front edge moved the feet only 0–1 step (the RF hip about 3). A few single samples read 5–10 steps off and are noise, so filter. So stock servos make poor touch sensors; options not yet tried: a softer P on the lifts (bigger deflections, but more sag, and calibrate and walking change), or the IMU (the gyro should see the rocking of a press; the BMI270 needs Bosch's 8 KB config blob loaded at init).
- **IMU:** a BMI270 at 0x68 on the internal I2C with the backlight (`sys_i2c_dev()` sets the bus up once). `imu_init()` soft-resets it, uploads Bosch's 8 KB config file (`atom/bmi270_config.h`, from BMI270_SensorAPI v2.86.1, BSD-3, the only other file the ATOM build includes) in 256-byte chunks, waits for INTERNAL_STATUS = 1, then sets accelerometer ±4 g at 100 Hz and gyro ±500 °/s at 200 Hz. The waits after the soft reset and PWR_CONF need to be real (5 ms each): with 1 ms ticks a `msleep(1)` can be almost nothing, and the upload then fails with init_err (status 2). The magnetometer (BMM150, behind the BMI270's aux interface) isn't set up. `imu_read()` rotates the chip's readings by `IMU_YAW` (−150°) into the robot's axes: +x towards the gap between legs 1 and 2, +y 90° anticlockwise from that seen from above, +z up. Found on 2026-10-05 with the ATOM in the new cage, lying flat on the leg 1–4 axis (chip +x at leg 4), by tipping the robot up at each gap in turn: the six tilts were 60° apart within ±10°, going clockwise. A couple of cm of lift is 6–20°, against 0.1° of noise, with the gyro at 8–25 °/s; setting it down jolts the accelerometer to about 1.15 g. At rest it reads a few degrees off level: about 1.7° of that turned with the robot when it was turned round on the desk (before the cage), so it's the robot's own (body on its legs, mounting, chip offset), the rest the desk. `imu [secs]` streams it; `selftest` reports pitch and roll.
- **Leg numbering:** legs 1–6 (hip ids) go clockwise round the body seen from above, so 1 and 4 are opposite (the user's numbering, confirmed with the IMU on 2026-10-05). The walk goes towards the gap between 6 and 1 (`legtest 1` swings leg 1's foot towards leg 6), so 1, 2, 3 are the right side front to back (RF, RM, RR) and 6, 5, 4 the left (LF, LM, LR). Until 2026-10-05 `legs[]` had an older wiring: 1–3 left and 4–6 right, both front to back, so the sides were swapped (turning was reversed and the leg names wrong) and 4 and 6 were each other's rows. `hip_dir` didn't change: a higher position turns every hip clockwise seen from above, so it's −1 for 1–3 and +1 for 4–6. The tripod groups are the same either way (1, 3, 5 and 2, 4, 6). The user doesn't think of the robot as having a front; the walk's is just where it goes.
- **`bow [secs]`:** stands and takes the IMU's reading as level (`bow_level()`, 0.5 s average). At 50 Hz, a tilt from level of over 3° is a tip; the direction at the biggest tilt is kept, counting only samples within 0.05 g of level's total (putting it down jolts the accelerometer to 1.1–1.16 g, in any direction, bigger than the tilt), and once it has been under 1.5° for 300 ms (put down and still) the lifts of the two legs either side of that direction (`leg_ang()`: leg k at 30 − 60(k−1)° in `imu_read()`'s axes) go to `BOW_POS` 700 (plus offset, as `move` would send) over `BOW_MS` 1000, hold `BOW_HOLD_MS` 500, then `stand(BOW_MS)`, and level is re-taken. The user designed the body to come down on that edge safely; their bow by hand was `stand; move 7-8 700 1000; stand`. Tested 2026-10-05 between legs 1 and 2 (lifts 7 and 8). The electronics sit in a separate hex cage on top (the robot looks like a phage); CAD for it not yet in `cad/`.
- **`sit [ms]`:** the user's switch-off pose (`move 7-12 1000 1000`): every lift to `SIT_POS` 1000 plus its offset, capped at 1003, hips untouched, sent with `sync_move()` directly as it's past `UP_MAX`. All 12 servos have angle limits 20..1003 (0x09/0x0B), so a goal above 1003 is clamped by the servo: lift 11 (offset +9) stopping at 1001 looked like it falling short, but it was on its clamped goal. The body sits on the ground and the legs point up inside it, safely, with no load on the servos. It sets each leg's z to match, though nothing reads it before the next `stand`.
- **Startup and `selftest`:** the self test is in two halves. `t_pre()` is the go/no-go for standing (screen and IMU answer, servos reply, battery, temperatures, error bits, overload settings, gains, positions); `t_standing()` needs the weight on the feet: each lift's goal, position, load and voltage in one 21-byte read from 0x2A, 5 times, giving the load on each foot (signed as in `calibrate`; warns over `FEET_SPREAD` 3% from the mean, or if the mean is under 2%: held up), sag (`lift_dir` × (position − goal), + = the foot pushed up by the weight; 2–4 is usual, warns over `SAG_MAX` 6), level (IMU, warns over `LEVEL_MAX` 5°), the highest load on any servo, and the battery under load. `t_end()` prints the result and puts Hi! on the screen. At power-on the ATOM runs `t_boot(1)`: `t_pre()`, then unless something failed `stand(1000)` and `t_standing()`, then `t_end()`; the Pi runs `t_boot(0)`, without standing. The `selftest` command runs `t_standing()` only if `standing` is set: `stand()` sets it, `sit()` and a walk frozen by ctrl-c clear it (other commands, `move` and so on, don't touch it). Opening the ATOM's USB port resets it, even with DTR and RTS held false, so connecting makes it stand up; the user is fine with that for now. **Foot loads and the I gain:** with the lifts at I 0 (before 2026-10-05), standing loads read only 0, 6, 7.5, 9% (one value per step a foot is pushed up), each stand left a different foot or two at 0, and `calibrate` couldn't settle (18 rounds of 1-step nudges just moved which feet read 0): it was measuring how the feet landed, not the offsets. With I 1 on the lifts (see Gains) they stand within about 1.5% every time, so the feet check is back at 3% and `calibrate` means something again. `t_standing()` waits 1 s after a stand first, for the I term to take up the weight (read at 0.2 s, two of four stands were still uneven). The IMU's tilt was steady through all of it (3.0–4.0°), about 1.7° of it the robot's own.
- **`set`:** the `params[]` table (gait, step, stride, lift, height) with ranges. The defaults are the gentle first-walk settings (wave, step 800, stride 50, lift 70, height 0), put back on 2026-09-26 while the user retunes for the new body; keep them until the user gives new values. The user's tuning on the old body was tripod, step 1000, stride 100, lift 100, height -60 (a slow, low, splayed walk that looked natural).

## Future ideas (for the ATOM S3R port; not started)

- **Startup calibration:** keep the table from a deliberate `calibrate` on a flat desk, saved to flash, as the reference. At startup, run `calibrate` from it with a tight cap (about ±8 steps instead of `CAL_MAX` 30) and use the result for that session only. If a leg hits the cap or it doesn't settle, fall back to the saved values and warn: that means a sagging servo (like the old servo 9), a loose horn, uneven ground or the robot being held. Startup corrections that grow over weeks would show servo wear. Offsets depend on `height`, so calibrate at the walking height or keep a set per height. Later, the same load readings could level each foot as it lands while walking.
- **The ATOM's screen** (0.85", 128×128, colour) as a status page: the startup check result (OK, or which leg hit its cap); six load bars laid out like the legs, standing or walking; battery from the servos' voltage register (2S is low at about 7.0 V); overload/overheat warnings by id and leg; the gait, stride and step, and whether it's walking. The gait code keeps its I/O in `send_pose()`/`send_leg()`, so the screen only needs to read the state it already has.
